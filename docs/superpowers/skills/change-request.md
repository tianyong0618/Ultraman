# 需求变更管理 (ChangeRequest) - Skill

## 概述

本技能为 Ultraman Magic Book 项目提供标准化的需求变更管理流程，确保所有变更可追溯、可验证，且始终与项目主规范对齐。

## 1. 技能触发方式

当用户说出以下任一指令时，自动激活本技能：

| 触发指令 | 动作 |
|---------|------|
| "帮我创建一个需求变更提案：[变更内容]" | 进入阶段1：创建提案 |
| "执行需求变更：[变更内容]" | 进入阶段1：创建提案 |
| "帮我归档本次变更" | 进入阶段5：归档 |
| "更新项目规范" | 进入阶段5：归档 |

## 2. 技能执行流程（强制5步闭环）

1. 读取 `docs/superpowers/specs/` 目录下的最新《ultraman-magic-book 项目需求说明书》作为基准

### 阶段 2：提案确认（必做）

**执行步骤：**

1. 等待用户明确回复"确认提案"或"同意执行"
2. 若用户提出修改意见，按意见更新提案，重新生成并再次等待确认
3. 只有用户确认后，才能进入开发阶段，禁止跳过此步骤直接修改代码

---

### 阶段 3：开发与验证（TDD 强制）

 **执行步骤：**

1. 按 TDD 原则，先补充单元测试用例，再实现变更功能
2. 严格遵循提案中的技术方案和执行步骤，不得擅自扩大变更范围
3. **【新增】每个 REQ 完成后立即更新文档**：
   - 在需求列表中将对应 REQ 标记为 ✅ 已完成
   - 在验收标准中将对应项标记为 [x]
   - 禁止：完成多个 REQ 后才批量更新
4. 执行全量验证：
   - 运行 `npm test` (Vitest 单元测试)
   - 运行 `npx playwright test` (E2E 测试)
   - 逐条验证提案中的所有验收条件

 **输出内容：**

- 开发进度与代码修改说明
- 完整测试报告与覆盖率变化
- 验证结果与通过情况
- **每个 REQ 的完成状态变化**

---

### 阶段 4：变更验收（必做）

**执行步骤：**

1. 向用户展示最终效果、测试报告和变更结果
2. 等待用户确认"验收通过"
3. 若用户提出调整意见，回到阶段3进行迭代修改，直至验收通过

---

### 阶段 5：归档与规范更新（必做）

 **执行步骤：**

1. 将本次变更内容更新到 `docs/superpowers/specs/` 目录下的主规范文档中
2. 补充版本历史记录
3. 整理变更前后的功能/代码对比说明
4. 确保所有文档与当前代码实现完全一致
5. 删除过时的临时文件
6. **【新增】交叉检查所有待实施提案**：列出 `docs/superpowers/specs/changes/` 目录下所有提案，检查每个提案的需求状态是否与实际代码状态一致，如不一致立即更新

 **交叉检查清单：**

| 检查项 | 动作 |
|--------|------|
| 列出所有变更提案 | 读取 `changes/` 目录下所有 `.md` 文件 |
| 检查每个提案的需求状态 | 对比文档状态与实际代码 |
| 更新不一致的提案 | 修正文档状态（标记为 ✅/❌/⏳） |
| 添加归档信息 | 如缺失，添加产出文件 + 需求汇总 |

 **输出内容：**

- 最终归档报告
- 交叉检查报告（多少提案被更新）
- 变更完成确认

## 3. 技能约束规则

| 规则 | 描述 |
|------|------|
| 规则1 | 禁止跳过提案或确认步骤直接修改代码 |
| 规则2 | 所有变更必须生成可追溯的文档，存放在 `docs/superpowers/specs/changes/` 目录 |
| 规则3 | 每次变更必须伴随对应的测试用例补充，且测试覆盖率不得低于当前水平 |
| 规则4 | 开发完成后必须执行全量回归测试，确保不影响现有功能 |
| 规则5 | 主规范文档必须与代码实现保持一致，禁止出现文档与代码脱节的情况 |
| 规则6 | 归档时必须交叉检查所有待实施提案，确保文档状态与实际代码状态一致 |
| 规则7 | 开发过程中必须逐个更新 REQ 状态，禁止批量更新 |
